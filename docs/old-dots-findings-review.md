# Review of old DOTS security findings

**Reviewed:** 2026-10-20  
**Scope:** Static comparison of the supplied old-DOTS findings with the current Laravel workspace.

## Executive assessment

The pasted report describes a CodeIgniter application under `C:\laragon\www\DOTS`. The current workspace is a Laravel application. I did not find the report's unauthenticated password-change path, non-admin account-role writes, or public setup shell endpoint in this source tree. Those exact account-takeover and privilege-escalation paths appear addressed in the current application code.

This does **not** prove that a deployed instance is safe or that no one exploited the old application. I could not inspect the production host, deployed files, live environment values, database, access logs, or credential-provider activity. The report also identifies remaining hardening and incident-response work below.

## Finding-by-finding assessment

| Unauthenticated password recovery / change can take over an account | **Not found in current source.** | Recovery returns the same generic response for matching and non-matching usernames. A reset is completed through Laravel's password broker using a token and the resolved account email; the request does not return a user UUID. The recovery-link request is throttled. The reset-submit route itself has no explicit throttle, so adding one is reasonable defense in depth. See [auth routes](../routes/auth.php#L24), [reset-link controller](../app/Http/Controllers/Auth/PasswordResetLinkController.php#L32), and [new-password controller](../app/Http/Controllers/Auth/NewPasswordController.php#L43). Account-management endpoints are inside an `administrator` group; that middleware requires `canManageLibraries()`, which checks role IDs 1 or 2. Create/update validation constrains submitted roles to configured role IDs or a fixed employee-role list. Role changes are audited with before/after values. See [web routes](../routes/web.php#L26), [administrator middleware](../app/Http/Middleware/EnsureAdministrator.php#L12), [role authorization](../app/Models/User.php#L100), and [account controller](../app/Http/Controllers/UserAccountController.php#L108). An administrator account compromise or unauthorized database write is outside this route-level protection. |

No `shell_exec`, `exec`, `system`, `passthru`, or `proc_open` call was found in application, bootstrap, route, config, or public PHP source. The workspace has CLI-oriented files under `scripts/`, not root-level HTTP helper endpoints. The web server must still use Laravel's `public/` directory as its document root. See [web routes](../routes/web.php#L71), [setup controller](../app/Http/Controllers/SetupController.php), and [public front controller](../public/index.php). |

Treat any credentials used by the old DOTS deployment as exposed until revoked, and verify deployed secrets separately. Keep the document root at `public/` so root-level environment and credential files are not web-served. |

The password-reset flow does not invalidate all other existing sessions. These records live in the application database, and no external append-only audit destination was verified. The current source scan found no shell-execution calls in HTTP code. This static review is not a complete SQL-injection or deployment audit. ## Adjacent issue

Guest registration remains enabled and is rate-limited. It does not expose the administrator-role write described in the old report, but confirm that self-registration is intended for this system. The existing [security review](../SECURITY_REVIEW.md) also tracks separate document-storage and public-tracking deployment checks; this review does not re-audit those findings.

## Actions before calling the deployed system safe

1. Verify the production release matches this Laravel source and that the web document root is `public/`; remove or isolate any old CodeIgniter deployment and its helper scripts.
2. Revoke and rotate credentials that appeared in old DOTS source or Git history, including the previously committed reCAPTCHA values. Confirm current SMTP, HRIS, PDMIS, iPluma, DRIP, database, and OAuth credentials with their owners; keep values out of this report.
3. Confirm production has `APP_ENV=production`, `APP_DEBUG=false`, HTTPS, and `SESSION_SECURE_COOKIE=true`. Check the TLS proxy and cookie behavior from the deployed site.
4. Consider throttling the reset-submit endpoint and revoking existing sessions after a successful password reset.
5. Review web/proxy, database, host, mail-provider, and integration-provider logs for the old endpoint paths and suspicious role/password changes. Preserve relevant logs and backups before rotation or cleanup. Source code alone cannot establish whether these paths were used.
6. Decide whether public registration is intended and disable it or add an enrollment policy if accounts should be provisioned only by administrators or HRIS.
